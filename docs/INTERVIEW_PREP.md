# ProcureFlow 面试准备

## 30 秒项目介绍

ProcureFlow 是面向制造企业物料采购的多智能体协同平台。我把业务拆成库存查询、供应商询报价和采购订单三个 Agent，由总控识别组合意图并通过 A2A 分发任务，各 Agent 再通过 MCP 调用 MySQL 领域服务。下单前采购订单 Agent 会并行核验库存与有效报价，写入阶段使用人工确认、幂等键、事务回滚和审计日志，避免大模型直接执行写 SQL。

## 业务链路怎么讲

用户先查询物料的在库量、占用量、可用量和安全库存，再按采购数量获取仍在有效期内的供应商阶梯报价。系统综合单价、最小起订量、交期、供应商评级和准时交付率给出比较。用户选择供应商后，订单 Agent 补齐申请人、物料、数量、单价和期望交期，展示预览并要求确认；确认后由数据库事务创建待审批采购单。

## 高频问题与回答要点

### 为什么适合多 Agent

库存、供应商和订单属于不同业务域，工具权限、数据表和失败处理不同。拆分后可以独立部署、独立扩展，也能限制订单 Agent 的写权限。组合查询可并行执行，订单创建则按依赖关系先核验再写入。

### A2A 和 MCP 分别解决什么问题

- A2A 解决 Agent 之间的发现、任务派发、状态和结果传递。
- MCP 解决 Agent 调用外部能力的标准化，把库存查询、报价查询和订单写入封装成工具。
- A2A 是 Agent 到 Agent，MCP 是 Agent 到工具或数据源，两者不是替代关系。

### 为什么不用一个大 Agent

单 Agent 容易把全部提示词、工具和权限放在一起，工具选择混乱，订单写权限也难隔离。多 Agent 的代价是调用链更长、故障点更多，所以总控要有超时、异常汇总、追问和降级策略。

### 创建采购单为什么不扣减库存

采购订单代表未来入库，不是销售出库。创建订单时只记录采购承诺，不应扣减或占用当前库存；到货并完成收货过账后才增加在库量。库存数据在下单前用于判断补货紧迫度和建议采购量。

### 如何防止重复下单

前端或调用方为一次业务请求生成 `idempotency_key`，数据库对该字段设置唯一约束。相同键重放时直接返回原采购单，不重复插入。唯一约束是最终保障，不能只靠应用内存判断。

### 如何保证报价可靠

下单事务中再次检查供应商状态、报价有效期、最小起订量和匹配的阶梯价，并比对用户确认的单价。面试时说明当前数据源是 JSON 模拟的 SRM 报价，真实项目应接 ERP/SRM 接口并保留报价版本。

### 如何防止大模型误写数据库

查询工具只接收结构化参数；如果扩展 Text-to-SQL，只允许单条 SELECT、表白名单和最大行数。INSERT/UPDATE 不接受模型生成的 SQL，而是走参数化领域方法，并要求人工确认、事务和审计。

### 供应商是不是最低价优先

不是。最低价可能伴随更长交期、较低准时交付率或较高起订量。当前系统返回价格、交期、评级和准时率，由规则排序并让模型解释；最终选择仍由采购人员确认。

### 异常怎么处理

Agent 返回 completed、input_required 或 failed 状态。缺字段时追问；某个查询 Agent 失败时总控保留其他成功结果并报告错误；订单写入任何一步失败都会回滚，调用方可使用同一幂等键安全重试。

## 需要掌握的采购术语

- 在库量：仓库账面已有数量。
- 占用量：已被订单、工单或领料需求预留的数量。
- 可用量：在库量减占用量。
- 安全库存：吸收需求和交付波动的缓冲库存。
- 采购提前期：从下单到可用入库所需时间。
- MOQ：最小起订量。
- 阶梯价：不同采购数量区间对应不同单价。
- 在途量：已经下单但尚未完成收货的数量。
- 三单匹配：采购订单、收货单、发票在付款前核对。

## 不要夸大的地方

- 这是课程实战和个人复现，不要说已在真实企业生产环境上线。
- 报价同步是模拟数据适配器，不要说已接入真实 ERP/SRM。
- 不要声称系统自动决定供应商；它提供比较与解释，采购人员最终确认。
- 不要只背框架名，要能打开 `db.py` 讲清事务、报价校验与幂等逻辑。
